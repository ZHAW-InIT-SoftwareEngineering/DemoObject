 Here’s a concrete, minimal plan to add MongoDB-backed session storage:

  - Define the data model: sessions collection with fields: sessionId (string, unique), token (string), path (string, optional until set), status (pending|ready), createdAt, expiresAt. Index on sessionId (unique) and expiresAt (TTL).
  - Add config: put Mongo URI and DB name in env (MONGO_URI, MONGO_DB). Decide collection name (sessions).
  - Connect once: create a Mongo client module that connects once on startup and exports the sessions collection handle.
  - Create service functions:
      - createSession(): generate sessionId + token, insert with status=pending, expiresAt=now+TTL, return IDs for QR payload (only IDs/tokens, not path).
      - setPath(sessionId, token, path): validate token, sanitize path, update path, status=ready, bump expiresAt if desired.
      - getSession(sessionId): fetch session; return path + status (don’t return token).
  - API routes:
      - POST /api/sessions: call createSession, return {sessionId, token} for QR.
      - POST /api/sessions/:id/path: body {path}, header/bearer includes token; call setPath.
      - GET /api/sessions/:id: return {status, path?} to let clients sync/recover on refresh.
  - Broadcast: on setPath, emit to connected clients in that session via websocket/SSE; clients subscribe by sessionId.
  - TTL cleanup: create TTL index on expiresAt to auto-delete stale sessions. Choose TTL (e.g., 15–60 min).
  - Validation/safety: validate path (length, allowed characters/directories), never put raw path in QR, use constant-time compare for token, return 401/404 appropriately.
  - Client flow:
      - Host: call create → render QR with sessionId+token.
      - User: scan QR → POST path with token → server stores & broadcasts.
      - Both: subscribe to websocket/SSE; on reconnect, call GET to resync.
  - Testing: happy path (create → setPath → read), bad token, expired session, TTL deletion (can mock time).
